SHOH PIZZA — 5 УРОК / BURP SUITE (ТОЛЬКО LOCALHOST)

Сайт выглядит как обычная пиццерия. Здесь НЕТ отдельной вкладки Authentication Lab. Учебные дефекты находятся непосредственно в формах Login / Forgot Password и обработке Session.

Старт: python3 app.py --reset    → http://127.0.0.1:8770
Безопасное сравнение: python3 app.py --secure --port 8771 (используйте отдельную копию проекта / БД для одновременного запуска)

Аккаунты (вымышленные):
customer: student@shohpizza.test / Pizza2026! / 246810
manager: manager@shohpizza.test / Manager2026! / 864200

Burp → Proxy → HTTP history; браузер через Burp proxy.

1) Username enumeration: POST /api/auth/login; сравнить существующий email с неверным паролем и несуществующий email. Разные HTTP 401 error сообщения vs единый ответ в --secure.
2) Login attempts: несколько ручных неверных запросов. Уязвимая версия не ограничивает число запросов; защищённая версия возвращает 429 после 5 попыток за 90 секунд. Никакой автоматизации перебора не нужно.
3) 2FA: после правильного пароля ответ 202. Уязвимый сервер преждевременно устанавливает sp_session; можно проверить GET /api/orders до отправки 2FA. В --secure — 401 до 2FA. Менеджерская функция требует MFA в обоих режимах.
4) Logout: перед выходом сохраните СВОЙ тестовый cookie. После нажатия Logout уязвимая реализация очищает cookie браузера, но не удаляет серверную сессию. Повторно посланный старый тестовый cookie остаётся действительным. В --secure — 401.
5) Password recovery: POST /api/auth/reset/request — разные ответы для вымышленного существующего и несуществующего email. В --secure сообщение одинаковое. Ссылка локального тестового ящика: GET /api/local-mailbox?email=student%40shohpizza.test
6) Менеджерская панель: только manager с завершённым MFA. Клиенту возвращается 403, это защита, не уязвимость.

Для сравнения сбросьте БД: python3 init_db.py --reset (остановите сервер перед сбросом). Все данные вымышленные. Не подключать внешние аккаунты и не публиковать сайт в интернете.
